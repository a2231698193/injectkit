# P1：JSON-RPC + 内存读取

## 端到端验证（实测）

```
1. 起目标进程 iktarget.exe (pid=11732)
2. ikloader 注入 → payload 基址 0x19e30000
3. ikclient 读目标内存
```

结果：

```
[mem.read] 0x7FF605110000 + 16
  status = ok
  got    = 16
  hex    = 4D5A90000300000004000000FFFF0000
  ascii  = MZ..............
```

**读到了目标进程的 PE 头。** 完整链路：

```
外部程序 → 命名管道 → JSON-RPC → payload → *ptr 读目标内存
```

## 三个关键设计决定

### 1. 为什么自己写 JSON

payload 跑在目标进程里，每多一个依赖就多一份体积和特征。而且：

- 只需要一个子集（解析命令 + 序列化结果）
- 不能依赖 CRT（manual map 下根本没初始化）
- 第三方库（nlohmann/json 等）会引入大量模板实例化，二进制膨胀

自己写的版本约 500 行，覆盖 object/array/string/number/bool/null，嵌套限 8 层防栈溢出。

### 2. 为什么用换行分隔而不是长度前缀

长度前缀更严谨，但换行分隔：

- 人肉调试直接 telnet 就能试
- Python/JS 客户端实现简单
- 我们传的都是文本（读到的字节用 hex 编码）

代价：字符串里的换行必须转义。JSON 序列化已经处理了。

### 3. `mem::read` 的三层保护

读任意地址最大的风险是**炸掉目标进程**。三层处理：

```cpp
1. 地址为 0 → 直接拒绝
2. VirtualQuery 查页属性 → 未提交/NOACCESS/GUARD 直接拒绝
3. 跨页时逐页推进 → 读到边界为止，返回 Partial + 实际字节数
```

**关键：绝不因为跨页就整块失败。** 返回 `Partial` 让调用方知道读到了多少。

`guard page` 单独识别 —— 这是 Warden 可能的诱饵（读它会被记录）。

## Warden 情报对设计的影响

`docs/warden-intel.md` 从 MaNGOS 服务端源码拿到了 Warden 的四类检查：

```
Timing (0x57)   时序
Lua    (0x8B)   Lua 状态
Mpq    (0x98)   文件完整性
Mem    (0xF3)   内存指定字节
```

**Mem 检查的机制**：服务端下发 `{moduleName + RVA, expectedBytes}`，客户端读那个地址→哈希→上报。

三个推论：

1. **Warden 不扫全场找特征码**，只读 N 个预定义地址
   → 它不会主动发现"进程里有块陌生的可执行内存"

2. **`moduleName + RVA` 意味着检查游戏模块内的代码字节**
   → **Detours hook 会让字节变 → 立刻被抓**

3. **Warden 不查句柄、不查模块列表**
   → LoadLibrary 注入和 manual map 对 Warden 影响不大

### 修正后的风险排序

| 行为 | 风险 | 原因 |
|---|---|---|
| Detours hook 游戏代码 | **极高** | Mem 检查直接命中 .text 变化 |
| 写游戏内存 | 高 | Mem 检查可能覆盖被改字段 |
| 改 Lua 状态 | 中 | Lua 检查 |
| 改游戏文件 | 高 | Mpq 检查 |
| **注入 + 只读** | **低** | 四类检查都不覆盖 |
| 外部只读 | 极低 | 同上，且无句柄检测 |

### 这对 injectkit 的定位意味着什么

**永远不做 hook。** 这是硬约束，不是可选项。

`mem.read` / `mem.chain` 是安全的——只读不改字节。

P4 的"调用游戏函数"需要仔细评估：如果调用本身不改变被检查的字节，就安全；如果要在函数开头写入跳转（Detours 的典型做法），就危险。

## 二进制审计

```
ikpayload.dll   敏感导入 0     ← 注入目标的部分，干净
ikloader.exe    敏感导入 4     ← OpenProcess / CreateRemoteThread /
                                 VirtualAllocEx / WriteProcessMemory
ikclient.exe    敏感导入 0     ← 外部主控，干净
```

`ikpayload.dll` 和 `ikclient.exe` 都拦掉了 MinGW 运行库带进来的 `OpenProcess`
（用 `--wrap=__imp_OpenProcess` 重定向）。只有 loader 需要它，因为注入本身
必须 `OpenProcess`。

## 踩过的坑

### 1. `PIPE_NOWAIT` 会丢连接

第一版 payload 用 `PIPE_NOWAIT` 想避免阻塞，结果：

```
ConnectNamedPipe → 立刻返回 ERROR_PIPE_LISTENING
ReadFile         → 立刻返回 got=0
```

管道在"等连接 / 断连重建"之间反复开关，客户端连上后服务端刚好重建，连接被丢弃。

**改成阻塞模式**（`PIPE_WAIT`），接受阻塞在 `ConnectNamedPipe` 上。退出时不管那个线程——进程结束自然结束。

### 2. `mem::chain` 最后一级必须验证可读

第一版只算出地址就返回 true。测试暴露了问题：

```
chain(base, {0x3C, 0xFFFFFF00}) → 返回 true，但地址根本不可读
```

这是 memkit 那边踩过的同一个坑：只算出地址不等于能用。改成最后一级也做一次读取探测。

### 3. `int64_t` 到 `Value` 的构造有歧义

```cpp
Value(int64_t)  // 与 Value(bool) / Value(double) / Value(int) 都匹配
```

加了显式的 `int64_t` 和 `uint64_t` 构造函数。

### 4. MinGW 会把 `OpenProcess` 带进 payload

即使 payload 一行都不用。用 `--wrap=__imp_OpenProcess` 重定向到空实现
——payload 根本不需要这个 API。
